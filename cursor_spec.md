## 1. Концепт (от заказчика, без изменений по смыслу)

- 3 падел-клуба Иркутска. Цель турнира: **больше игр на всех трёх площадках**.
- 30+ участников, **3 дивизиона по 10**, в каждом **2 призовых места**.
- Сначала отборочные (квалификационные) матчи, затем распределение по дивизионам **по числу побед**.
- **Пары фиксируются при регистрации.** Игроку без пары система даёт **случайного напарника на каждый матч**.
- Матчи: игроки **сами договариваются** о времени, играют **в течение недели** на **любой из 3 площадок**. **Несыгранный матч = техническое поражение.**
- Результат: выигравший вносит, соперник подтверждает; либо скриншот Lunda, админ подтверждает.
- Рейтинг Lunda: открытого API нет → в приложении свой рейтинг по аналогии с Lunda; игрок указывает свой рейтинг Lunda, админ сверяет по скриншоту. **TODO: написать в Lunda про интеграцию для партнёров** (см. §14, вопрос 20).
- Взнос **4000 ₽ с пары**: 30% организатору, 70% в призовой фонд. Фонд делится между дивизионами **60 / 30 / 10** (ДОПУЩЕНИЕ: 60% получает верхний дивизион).
- Оплата через **ЮMoney с автоподтверждением по HTTP-уведомлениям**. Просьба заказчика была «со СБП» — см. §10: форма ЮMoney для кошелька СБП не предлагает, нужно решение заказчика.
- Срок: **один месяц**. Финалы **офлайн в клубе**, с записью и награждением.
- Спонсоры: **скидки клубов, логотипы в приложении**.
- Дизайн лаконичный: главная, регистрация в 1 тап через Telegram, мои матчи, таблица, профиль, сетка. Плюс админка.

Факты о Lunda, проверенные 3 ноября 2026 (источник: https://www.lundapadel.com/ и описания в магазинах приложений): шкала рейтинга игроков 1,0–7,0, рейтинг считается автоматически и подтверждается тренерами; на сайте заявлено, что базовое ПО бесплатно; публичной документации API там нет. Эту шкалу мы используем для поля «рейтинг Lunda», но **не копируем их алгоритм**.

| A12 | Название, сроки (регистрация, старт, финал), площадки, партнёры и спонсоры **редактирует админ в процессе**. Игрок только читает опубликованное. | админка `/admin` |

| A3 | Формат: квалификация **2 тура по 7 дней** → распределение по дивизионам → плей-офф в каждом дивизионе до финала. Дивизионы 10/10/остаток. | `TournamentConfig.qualRounds`, `divisionSizes` |
| A4 | Матч до 2 побед в сетах (best of 3). Третий сет — обычный (не супертай-брейк). | `TournamentConfig.matchFormat` |
| A5 | Плей-офф дивизиона из 10: плей-ин (7–10, 8–9) → 1/4 → 1/2 → финал. Пары 1–6 в плей-ине не играют. Призовые места: 1-е и 2-е (финалисты). | `TournamentConfig` |

| A9 | В плей-офф одиночки внутри дивизиона получают **постоянного напарника на весь плей-офф** (балансируем по рейтингу), потому что сетка не работает с меняющимся составом. | `soloPlayoffMode` |
| A10 | Комиссию ЮMoney платит организатор (плательщик платит ровно 4000 ₽), она уменьшает долю организатора, а не призовой фонд. | `commissionPayer` |
| A11 | Рейтинг «как у Lunda»: свой Elo-подобный рейтинг турнира. Стартовое значение берётся из указанного рейтинга Lunda по линейной формуле (§8.9). | `initialRating` |

## 4. Дизайн-бриф

### 4.1. Принципы

1. **Минимум кнопок на экране.** На экране одно главное действие (крупная кнопка), максимум одно-два второстепенных. Всё остальное — информация, а не управление.
2. **Понятно с первого взгляда.** Любой экран читается за 3 секунды: что происходит, что делать мне. Никаких скрытых жестов и значков без подписей.
3. **Крупные цели касания: не менее 44–48 px по высоте и ширине** (iOS HIG рекомендует 44 pt, Material Design — 48 dp; промежутки между целями не менее 8 px). Основные кнопки — 52 px. Табы нижней навигации — 64 px. Строки таблицы — 48 px. Кнопки «+/−» — 56 px.
4. Текст не мельче 14 px (подсказки), основной 16 px, поля ввода не мельче 16 px (иначе iOS приближает страницу).
5. Цвета брать из темы Telegram (`--tg-theme-*`), поддерживать светлую и тёмную темы; один акцентный цвет. Статусы: победа/ок — зелёный, ожидание — янтарный, поражение/спор — красный; цвет всегда дублируется текстом.
6. Учитывать безопасные зоны (`--tg-safe-area-inset-*`), нижняя навигация не должна перекрывать главную кнопку.
7. Использовать нативные элементы Telegram: `MainButton` для главного действия, `BackButton`.
8. Анимации плавные (60 fps), на слабых Android-устройствах отключать лишние эффекты.
9. Все изображения и поля имеют подписи (accessibility).

### 4.3. Что НЕ делать

- Не копировать чужую айдентику, логотипы и макеты; брать приёмы, а не оформление.
- Не делать экран «со всем сразу». Если на экране больше трёх разных действий — разбить на экраны или спрятать в шторку.
- Не использовать иконки без подписи в нижней навигации.

### 4.4. Навигация

Нижний таб-бар из 5 пунктов: **Главная · Матчи · Таблица · Сетка · Профиль**. Регистрация открывается главной кнопкой «Участвовать» и после оплаты исчезает. Админка доступна только админам, отдельным маршрутом `/admin` (ссылка в Профиле, видна только роли ADMIN/OWNER).

## 5. План разработки по этапам

Общее правило для каждого этапа: Cursor работает в отдельной ветке, делает небольшие коммиты и в конце запускает `pnpm lint && pnpm typecheck && pnpm test && pnpm build` — всё зелёное. После этапа — короткая запись в `CHANGELOG.md`.

### Этап 0. Визуальная база через Stageshow (React-макеты 6 экранов)

**Что такое Stageshow** (по SKILL.md в https://github.com/benjitaylor/skills/tree/main/stageshow, прочитан 3 ноября 2026). Это skill для агентов (Cursor и др.), который строит «вымышленный интерфейс продукта» (faux UI) на React и обычном CSS: окна, телефоны (`Phone` сам рисует статус-бар и индикатор), дашборды, уведомления, анимированные демо с курсором. Внутри — kit (`Stage`, `Phone`, `Window`, `Row`, `Bar`, `Text`, `Segmented`, `Tabs`, `Badge`, `Chip` и др.), набор эталонных примеров (в т.ч. `phone-touch` — приложение на телефоне, `swipe`, `form-error`, `table-edit`) и справочники `references/craft.md`, `framing.md`, `motion.md`. Skill требует сначала написать план кадра (что в фокусе, какое действие, что можно опустить), выбрать ближайший эталонный пример, скопировать его и подставить свой продукт; настоящий текст ставится только там, где он несёт смысл, остальное — серые плашки-заглушки; у каждого движения есть причина. Установка (из репозитория skill): `npx skills add benjitaylor/skills --skill stageshow`, запускать в корне нашего проекта.

**Как используем и чего не ждём.** Stageshow рассчитан на иллюстрации и промо-анимации, а не на боевой UI. Здесь он нужен **для быстрой, хорошо скомпонованной визуальной базы**: шесть макетов экранов внутри `Phone` в светлой и тёмной теме. Из макетов берём компоновку, отступы, иерархию, типографику и токены цветов. **Компоненты боевого приложения пишем заново** (у них другие требования: доступность, тема Telegram, реальные данные) — макеты Stageshow в production не импортируем.

**Задачи:**
1. Установить skill (команда выше), прочитать `SKILL.md`, `references/craft.md` и `references/framing.md`.
2. Написать `design/PLAN.md`: для каждого экрана — что в фокусе, главное действие, что можно опустить.
3. Создать `design/mockups/` (отдельное Vite-приложение, не входит в `apps/*`). Шесть макетов, каждый в `Phone`: Главная, Регистрация, Мои матчи, Таблица, Сетка, Профиль (тексты и данные — по §6 и по демо `demo/`).
4. Страница-обзор `design/mockups/src/Overview.tsx`: шесть макетов рядом и переключатель тёмной темы.
5. Выписать токены в `design/tokens.md`: цвета (акцент, фон, карточка, статусы), радиусы, размеры шрифтов, отступы, высоты кнопок и строк.
6. Заполнить `design/REVIEW.md`: проверка каждого макета по правилам §4 (число кнопок, размеры целей ≥ 44–48 px, читаемость за 3 секунды).

**Критерии приёмки:**
- [ ] `design/mockups` запускается (`pnpm --filter mockups dev`) и собирается (`build`) без ошибок.
- [ ] Все 6 экранов присутствуют; на каждом не больше одной главной кнопки и двух второстепенных; цели касания ≥ 44 px.
- [ ] Есть светлая и тёмная темы; сохранены скриншоты в `design/screens/`.
- [ ] Нет выдуманных названий клубов, спонсоров, реальных людей; заглушки подписаны.
- [ ] `design/tokens.md` содержит значения, которые потом идут в CSS-переменные `apps/web`.
- [ ] Заказчик утвердил макеты. Без утверждения этап 1 можно вести параллельно, но экраны этапа 2+ верстаются по утверждённым макетам.

### Этап 1. Каркас, окружение, авторизация

Задачи: pnpm-монорепо; `docker-compose.yml` (postgres); Prisma-схема из §7, первая миграция и сид (клубы-заглушки, один турнир в статусе `REGISTRATION`); Fastify-API с `/health`; grammY-бот (`/start` с кнопкой «Открыть турнир», webhook); Mini App с темой Telegram, роутингом, нижним таб-баром (5 пунктов, пустые экраны по макетам); **авторизация по initData** (§9.1) и выдача JWT; роли PLAYER/ADMIN/OWNER (списки Telegram-ID в `.env`); `.env.example`.

Критерии приёмки:
- [ ] `docker compose up -d && pnpm dev` поднимает всё локально; `pnpm prisma migrate dev` и сид проходят.
- [ ] Открытие Mini App из бота создаёт/обновляет `User`; `GET /me` возвращает профиль.
- [ ] Подделанный или просроченный initData (старше `INITDATA_MAX_AGE_SEC`, по умолчанию 3600) → 401. Есть юнит-тест на проверку подписи.
- [ ] Тема Telegram подхватывается, светлая и тёмная корректны, safe area учтена.
- [ ] Админ из `.env` видит пункт «Админка», обычный игрок — нет.

### Этап 2. Регистрация и оплата

Задачи: экран «Регистрация» (§6.2); создание `Entry` типа PAIR или SOLO; приглашение напарника по deep link (`startapp=inv_<code>`), принятие приглашения; поле «рейтинг Lunda» с шагом 0,1 (1,0–7,0) и статусом проверки; создание `Payment` и страница оплаты ЮMoney (§10); приём HTTP-уведомлений ЮMoney с проверкой подписи `sign`; автоматическая активация записи; уведомление в бот «Вы в турнире»; админка: список записей, ручная отметка оплаты (с причиной), закрытие регистрации.

Критерии приёмки:
- [ ] Пара: капитан регистрируется, напарник принимает приглашение, платёж создаётся один на пару; после уведомления запись `ACTIVE`.
- [ ] Одиночка: регистрируется без напарника, платит свой взнос, получает статус `ACTIVE`.
- [ ] Уведомление ЮMoney с неверной подписью отклоняется (HTTP 400); повторное уведомление с тем же `operation_id` не создаёт дубль; сумма меньше ожидаемой → платёж `MISMATCH`, запись не активируется, админ видит предупреждение.
- [ ] Повторное нажатие «Оплатить» не создаёт второй платёж, пока первый не истёк.
- [ ] Регистрация закрывается автоматически в `registrationClosesAt`; новая запись после — 409.
- [ ] Юнит-тесты на подпись, идемпотентность и проверку суммы.

### Этап 3. Квалификация: жеребьёвка туров, матчи, результаты, дедлайны

Задачи: генерация тура (§8.2, §8.3) с предпросмотром для админа и публикацией; экран «Мои матчи» (§6.3); внесение результата победителем, подтверждение соперником, спор; загрузка скриншота Lunda и подтверждение админом; техническое поражение по дедлайну (cron); напоминания; запись площадки, где играли; админ может править результат с записью в аудит.

Критерии приёмки:
- [ ] Для 30 пар тур строится без повторов соперников; при нечётном числе сторон бай получает запись, у которой его ещё не было.
- [ ] Для набора из 6 одиночек + 6 пар жеребьёвка создаёт временные пары, не повторяя напарников из прошлых туров, если это возможно; сид сохранён и воспроизводим (одинаковый сид → одинаковый результат, тест).
- [ ] Победитель вносит счёт по сетам и площадку; соперник подтверждает → матч `CONFIRMED`; не подтверждает 48 ч → авто-подтверждение (§8.5); оспаривает → `DISPUTED`, админ получает задачу.
- [ ] В 23:59 по Иркутску в последний день тура необработанный матч получает тех. поражение (§8.4); двойное тех. поражение обеим сторонам; в плей-офф без решения админа матч не закрывается автоматически.
- [ ] Напоминания приходят за 72, 24 и 3 часа до дедлайна, по одному разу каждое.
- [ ] Все изменения результатов пишутся в `AuditLog`.

### Этап 4. Таблица, распределение по дивизионам, рейтинг

Задачи: пересчёт таблицы после каждого подтверждённого матча (§8.6); экран «Таблица» (§6.4); формирование дивизионов (§8.7) с предпросмотром и публикацией; рейтинг турнира (§8.9); проверка рейтинга Lunda админом по скриншоту (очередь в админке); профиль игрока (§6.6).

Критерии приёмки:
- [ ] Таблица соответствует правилам тай-брейков (§8.6); есть тесты на каждый уровень тай-брейка и на жребий.
- [ ] После окончания квалификации админ видит предпросмотр дивизионов (10/10/остаток) и публикует; после публикации состав не меняется без записи в аудит.
- [ ] Ручная правка рейтинга Lunda админом сохраняет скриншот, значение «до/после» и автора.
- [ ] Экран «Таблица»: моя строка подсвечена, переключение дивизионов одним касанием.

### Этап 5. Плей-офф и сетка

Задачи: генерация сетки по §8.8 (плей-ин, автоматическое продвижение победителей); экран «Сетка» (§6.5) с горизонтальной прокруткой раундов; сроки раундов; формирование постоянных пар одиночек для плей-оффа; страница финала (дата, клуб, ссылка на видео — вводит админ); определение призёров и расчёт призовых.

Критерии приёмки:
- [ ] Для дивизиона из 10 строится сетка «плей-ин 7–10 и 8–9 → 1/4 → 1/2 → финал»; пары 1–6 автоматически проходят в 1/4; для 8, 9, 11, 12 и 16 участников сетка тоже строится верно (тесты).
- [ ] Победитель подтверждённого матча автоматически занимает слот следующего матча.
- [ ] Призовые считаются по §8.10 из фактически оплаченных записей, суммы в копейках; выплаты + доля организатора = собранные взносы.
- [ ] Моя пара подсвечена на сетке; переключаются все три дивизиона.

### Этап 6. Админ-панель (может идти параллельно с этапами 2–5)

Разделы и действия — §6.8. Критерии приёмки:
- [ ] Недоступна обычному игроку (403 по API, нет в UI).
- [ ] Каждое действие, меняющее результат, оплату, рейтинг или состав, пишется в `AuditLog`.
- [ ] Экспорт участников и платежей в CSV.
- [ ] Рассылка через бота: предпросмотр, отправка одной кнопкой, лимит скорости (не больше 25 сообщений в секунду), отчёт «доставлено/ошибки».

### Этап 7. Спонсоры, уведомления, финал, выпуск

Задачи: блок «Партнёры» (логотипы, скидки клубов из админки); уведомления бота по всем событиям (§9.5); страница «Финал и награждение»; текст правил и политики конфиденциальности (вводит заказчик); сквозной тест на тестовом боте; деплой на сервер заказчика; ежедневные бэкапы Postgres.

Критерии приёмки:
- [ ] Прогон «весь турнир на 12 тестовых пар за один день» (сидер ускоряет сроки) проходит без ручных правок БД.
- [ ] Логотипы спонсоров отображаются на Главной, скидки видны в карточке клуба.
- [ ] Бэкап БД создаётся и восстанавливается (проверено вручную).
- [ ] `RUNBOOK.md`: как поднять, как продлить срок матча, как вручную подтвердить оплату, как отменить турнир и вернуть деньги.

## 6. Экраны (спецификация)

Для каждого экрана: цель, содержимое, действия, состояния. Размеры целей касания — по §4. Ориентир по компоновке — `demo/`.

### 6.1. Главная

Цель: за 3 секунды понять, на каком этапе турнир и что мне делать.

Сверху вниз:
1. Заголовок турнира и чип этапа: «Квалификация · тур 1 из 2 · осталось N дней» (чип показывает ближайший дедлайн).
2. **Главный блок (одно действие):**
   - не зарегистрирован → кнопка «Участвовать в 1 тап · 4 000 ₽ с пары» (ведёт на «Регистрация»);
   - зарегистрирован, оплата не прошла → «Оплатить»;
   - есть матч, требующий действия → карточка «Следующее действие» (внести результат / подтвердить результат / договориться с соперником) → «Матчи»;
   - нечего делать → карточка «Следующий матч — после жеребьёвки тура, срок …».
3. Карточка «Призовой фонд»: общий и по дивизионам (расчёт по §8.10; пока регистрация открыта подпись «расчёт на N пар»).
4. Карточка «Площадки»: три клуба (название, адрес, ссылка на карту — вносит админ); подсказка «Играйте на любой из трёх».
5. Карточка «Партнёры турнира»: логотипы спонсоров (нажатие — карточка спонсора и скидка для участников).

Состояния: загрузка (скелетоны), ошибка сети (кнопка «Повторить»), турнир завершён (блок призёров).

### 6.2. Регистрация (1 тап через Telegram)

Цель: записаться и оплатить с минимумом шагов. Имя, фото и Telegram-ID берутся из initData — **ни одного поля «ФИО/телефон»**.

Содержимое:
1. Переключатель **«Парой» / «Один»** (две крупные кнопки, по умолчанию «Парой») и подсказка под ним: пара фиксируется на весь турнир; одиночке подбирают случайного напарника на каждый матч.
2. Блок «Ваш рейтинг Lunda»: степпер 1,0–7,0 с шагом 0,1, кнопки «−» и «+» 56 px, крупное число. Подпись «Админ проверит по скриншоту». Необязательная загрузка скриншота (можно позже в Профиле).
3. Для пары: кнопка «Пригласить напарника» (делится ссылкой `https://t.me/<bot>/<app>?startapp=inv_<code>` через Telegram share). Оплатить можно сразу — напарник присоединится по ссылке; запись активируется, когда есть оплата **и** напарник принял приглашение (§8.1).
4. Закреплённая внизу главная кнопка (`MainButton`): «Оплатить 4 000 ₽» (пара) или «Оплатить 2 000 ₽» (одиночка, A2). Нажатие открывает платёжную страницу ЮMoney.
5. После возврата — экран-подтверждение «Оплата получена, вы в турнире». Если уведомление ещё не пришло: «Проверяем оплату…» с опросом статуса каждые 5 секунд до 2 минут, затем «Если оплатили, а статус не изменился — напишите организатору» и кнопка связи.

Правила: один пользователь — одна запись в турнире; пользователь не может быть напарником в двух записях; выход из турнира до закрытия регистрации (возврат — §14, вопрос 11).

### 6.3. Мои матчи

Цель: видеть только мои матчи и одно действие по каждому.

Карточка матча: этап («Квалификация, тур 2»), стороны (я с напарником против соперников), срок «до 8 ноября, 23:59» с обратным отсчётом, статус-плашка и одна основная кнопка по статусу:

| Статус | Что видит игрок | Главная кнопка | Второстепенная |
|---|---|---|---|
| `SCHEDULED` | срок, username соперника | «Внести результат» | «Написать сопернику» (открывает `https://t.me/<username>`; если username скрыт — текст «соперник получит ваше уведомление от бота») |
| `RESULT_SUBMITTED` (внёс соперник) | счёт и площадка | «Подтвердить» | «Спор» |
| `RESULT_SUBMITTED` (внёс я) | «Ждём подтверждения соперника, авто через N ч» | — | «Исправить» (пока соперник не подтвердил) |
| `CONFIRMED` | счёт, площадка, «Победа/Поражение» | — | — |
| `DISPUTED` | «Спор рассматривает организатор» | — | — |
| `TECH_LOSS` | «Техническое поражение: матч не сыгран в срок» | — | — |
| `BYE` | «В этом туре у вас свободный круг» | — | — |

Внесение результата — нижняя шторка: быстрый выбор счёта по сетам «2:0 / 2:1 / 1:2 / 0:2», затем геймы по каждому сету (степперы), площадка (один из трёх клубов), необязательно «Прикрепить скриншот Lunda» (тогда результат подтверждает админ, §8.5). Единственная главная кнопка — «Отправить».

Кнопка «Соперник не выходит на связь» появляется за 48 часов до дедлайна и открывает форму (текст + необязательный скриншот переписки); админ учтёт её при тех. поражении (§8.4).

### 6.4. Таблица

Вкладки: «Квалификация» (до распределения), затем «Див. 1 / Див. 2 / Див. 3». Строки (48 px): место, пара (имена), игры (И), победы (В), разница сетов (Δ). Моя строка подсвечена и автоматически прокручивается в видимую область. Нажатие на строку — шторка с историей матчей пары. Под таблицей одна строка с правилами сортировки.

### 6.5. Сетка

Вкладки дивизионов. Горизонтально прокручиваемые колонки-раунды: «Плей-ин → 1/4 → 1/2 → Финал (офлайн)». Матч — карточка из двух строк (48 px каждая): пара, счёт, победитель выделен жирным; пустой слот подписан «Победитель 4–5». Моя пара подсвечена. Нажатие на матч — шторка с деталями (срок, площадка, действие, если матч мой).

### 6.6. Профиль

Аватар и имя (из Telegram), статистика (матчи, победы, площадки), блок «Рейтинг»: рейтинг турнира, указанный рейтинг Lunda со статусом проверки («Ждёт проверки» / «Подтверждён» / «Отклонён: причина») и кнопка «Загрузить скриншот Lunda». Напарник, статус оплаты. Для админа — пункт «Админка».

### 6.7. Финал и награждение

Дата, клуб и время (вводит админ), список финалистов, после игры — призёры и ссылка на запись (`finalsVideoUrl`).

### 6.8. Админ-панель (`/admin`, только ADMIN/OWNER)

Мобильная вёрстка по тем же правилам (крупные цели). Разделы:
1. **Обзор:** число записей, оплат, матчей без результата, споров, рейтингов в очереди.
2. **Записи:** список, фильтры (оплачено/нет, пара/одиночка), ручная отметка оплаты, снятие записи с причиной.
3. **Рейтинги Lunda:** очередь скриншотов; «Подтвердить значение», «Изменить значение», «Отклонить (причина)».
4. **Матчи:** фильтры по статусу/туру; споры; подтверждение результата по скриншоту Lunda; ручное внесение/правка результата; присуждение тех. поражения; продление срока одного матча (с причиной).
5. **Туры и жеребьёвка:** создать тур → **предпросмотр пар** (с сидом, можно перегенерировать, можно вручную поменять пары) → «Опубликовать» (рассылка игрокам).
6. **Дивизионы и сетка:** предпросмотр дивизионов → публикация; генерация сетки; ручное назначение пар одиночек для плей-оффа.
7. **Призовые:** расчёт по дивизионам и местам; отметка «выплачено» с датой.
8. **Клубы и спонсоры:** CRUD (название, адрес, ссылка на карту, логотип, текст скидки, порядок показа).
9. **Настройки турнира:** даты, взносы, доли, формат (`TournamentConfig`, §8.0).
10. **Рассылка:** текст + кнопка «Открыть», предпросмотр, отчёт.
11. **Журнал (AuditLog)** и **экспорт CSV**.

## 8. Бизнес-правила

### 8.0. Конфигурация турнира (`Tournament.config`, тип `TournamentConfig`)

```ts
interface TournamentConfig {
  qualRounds: number;                 // 2 (A3)
  qualRoundDays: number;              // 7
  playoffRoundDays: { playIn: number; quarter: number; semi: number }; // 4, 5, 5
  divisionSizes: Array<number | 'rest'>; // [10, 10, 'rest'] — последний = остаток
  divisionsCount: number;             // 3
  matchFormat: { setsToWin: 2; thirdSet: 'full' | 'superTiebreak' };   // A4
  byeCountsAsWin: boolean;            // true (A7)
  confirmTimeoutHours: number;        // 48 (A8)
  resultGraceHours: number;           // 12: сколько после дедлайна ещё можно внести результат матча, сыгранного вовремя
  inviteExpiresHours: number;         // 72
  soloPlayoffMode: 'fixedPairsByRating'; // A9
  commissionPayer: 'organizer' | 'payer'; // A10
  reminders: number[];                // часы до дедлайна: [72, 24, 3]
  initialRating: { base: number; perLundaPoint: number; lundaAnchor: number }; // A11
  rating: { k: number };              // коэффициент Elo, по умолчанию 32
  fillFromPlaces: number[];           // A1: [3, 4] — добор в дивизион с этих мест
  drawModes: Array<'auto' | 'manual'>; // A14
}
```

Все дедлайны — **23:59:59 по Asia/Irkutsk последнего дня тура**. Хранить в UTC, считать библиотекой дат с поддержкой часовых поясов (`date-fns-tz` или `luxon`); не прибавлять «+8 часов» вручную.

Расписание по умолчанию (A3, итого 28 дней + финал): квалификация тур 1 — 7 дней, тур 2 — 7 дней; распределение по дивизионам — публикация в день после тура; плей-ин — 4 дня; 1/4 — 5 дней; 1/2 — 5 дней; финал офлайн — в последние дни месяца. Если заказчик захочет 3 квалификационных тура, плей-офф придётся сжать или удлинить турнир (§14, вопрос 6).

### 8.1. Регистрация и активация записи

1. `Entry` создаётся в статусе `PENDING_PAYMENT` (одиночка) или `PENDING_PARTNER` (пара, пока напарник не принял приглашение).
2. Платёж создаёт капитан; для пары один платёж 4000 ₽ на пару.
3. Запись становится `ACTIVE`, когда выполнены **оба** условия: платёж `PAID`/`MANUAL_PAID` **и** (одиночка или напарник принял приглашение).
4. Если оплата прошла, а напарник не принял приглашение за `inviteExpiresHours` — капитану приходит напоминание; решение за организатором (§14, вопрос 11).
5. Приглашение — ссылка с `inviteCode`; принять может любой пользователь без другой записи; капитан может отозвать приглашение, пока оно не принято.
6. Регистрация закрывается в `registrationClosesAt` или кнопкой админа. После закрытия новые записи — 409.
7. Если к закрытию записей меньше 18 (по 6 на дивизион) — админу предупреждение и выбор: перенос срока или меньше дивизионов.

### 8.2. Жеребьёвка квалификационного тура

Вход: все `ACTIVE`-записи, история прошлых туров, сид.

1. **Составить стороны.**
   - Каждая запись типа PAIR — отдельная постоянная сторона (одна `Side`, одна `Entry`).
   - Записи SOLO перемешать генератором, инициализированным сидом (`Round.seed`, сохраняется в БД), и собрать временные пары: два одиночки в одной `Side` (`isTemporary = true`).
   - Ограничение: не ставить в пару людей, уже бывших напарниками в прошлых турах (если вариантов нет — снять ограничение и пометить это в предпросмотре).
   - Одиночек нечётное число: один одиночка остаётся без пары и получает бай (приоритет — у кого бая ещё не было; среди таких — по сиду).
2. **Составить матчи.** Стороны перемешать и искать полное паросочетание, где никто не играет с прошлым соперником (поиск с возвратом, лимит 2000 попыток). Не нашлось — разрешить повторы с минимальным их числом и показать предупреждение.
3. Сторон нечётное число: одна сторона получает бай (та же логика приоритета). Один и тот же участник не получает бай дважды, пока есть другие варианты.
4. Бай записывается как `Match` со `status = BYE`, `sideBId = null`; победа засчитывается по `byeCountsAsWin`.
5. Результат жеребьёвки сохраняется как **черновик** (`Round.status = DRAFT`): админ видит пары, может перегенерировать (новый сид) или вручную поменять, затем «Опубликовать». После публикации игроки получают сообщение бота.
6. Все матчи тура получают одинаковый `deadlineAt` — конец последнего дня тура.

Нужен детерминированный генератор псевдослучайных чисел (например `seedrandom` или mulberry32), сид — строка. Юнит-тест: одинаковый сид и вход → одинаковый выход.

### 8.3. Матчи одиночек (каждый матч — новый напарник)

- В квалификации каждый тур формирует новые временные пары одиночек (§8.2).
- Победа/поражение засчитываются **каждому из двух одиночек** стороны (`Standing` обеих записей).
- Рейтинг турнира меняется каждому игроку по формуле §8.9 на основе среднего рейтинга стороны.
- Если один из партнёров временной пары не явился: сторона получает тех. поражение, по умолчанию оба одиночки получают его в таблицу; админ может снять поражение с «пришедшего» по его заявке (`noShowClaim*`).

### 8.4. Сроки и техническое поражение

Матч должен быть **сыгран и внесён** до `deadlineAt`.

| Ситуация на `deadlineAt` | Итог |
|---|---|
| Результат внесён и подтверждён | как есть |
| Результат внесён, не подтверждён | ждём подтверждение до `confirmTimeoutHours` после внесения, затем авто-подтверждение (A8); спор — решает админ |
| Результат не внесён, нет заявки «не выходит на связь» | в **квалификации**: `TECH_LOSS` обеим сторонам (`BOTH`), победы нет ни у кого; в **плей-офф**: `NEEDS_ADMIN` |
| Результат не внесён, есть заявка одной стороны | `NEEDS_ADMIN`: админ выбирает «тех. поражение стороне А / Б / обеим»; если админ не решил за 24 часа — в квалификации применяется правило строки выше, в плей-офф ждём админа и шлём ему напоминания |
| Матч сыгран вовремя, результат внесён в течение `resultGraceHours` после дедлайна | принимается с пометкой «поздно», подтверждение как обычно |

- Тех. поражение не меняет разницу сетов и геймов (в тай-брейках не учитывается), увеличивает `techLosses` и `played`; рейтинг турнира тех. поражением не меняется (рейтинг только за сыгранные матчи).
- Админ может **продлить срок одного матча** с причиной; запись в `AuditLog`.
- Cron раз в 5 минут находит матчи с `deadlineAt < now()` в статусах `SCHEDULED/RESULT_SUBMITTED`; обработка идемпотентна (повторный запуск ничего не меняет).
- Напоминания за 72/24/3 часа шлются только по матчам без результата; дедупликация по `Notification.dedupeKey`.

### 8.5. Результаты: два пути

**Путь 1 — вручную.** Игрок стороны-победителя вносит: счёт по сетам, площадку (`clubId`), дату `playedAt` (по умолчанию «сегодня»). Статус `RESULT_SUBMITTED`. Любой игрок проигравшей стороны нажимает «Подтвердить» → `CONFIRMED`, `resultSource = PLAYER_CONFIRMED`. «Спор» → `DISPUTED`, решает админ. Если соперник молчит `confirmTimeoutHours` — `AUTO_CONFIRMED` (A8; §14, вопрос 9). Пока соперник не подтвердил, внёсший может исправить счёт — тогда подтверждение запрашивается заново.
- Валидация счёта: у победителя 2 сета, всего 2–3 сета; геймы в сете 0–7, допустимые значения 6:0…6:4, 7:5, 7:6 (если выбран `superTiebreak` для третьего сета — по правилам этого формата). Невалидный счёт не принимается.
- Если результат хочет внести проигравшая сторона, система сама определяет победителя по счёту, а подтверждает другая сторона.

**Путь 2 — скриншот Lunda.** Игрок прикрепляет скриншот результата из Lunda (`MatchProof`, `kind = LUNDA_RESULT`) и вносит счёт. Статус `RESULT_SUBMITTED` с флагом «нужен админ»; подтверждает **админ** (`resultSource = LUNDA_SCREENSHOT`), сверяя счёт по картинке; он может исправить счёт.

Права: вносить и подтверждать могут только игроки сторон матча и админы. Файлы: jpeg/png/webp, до 10 МБ, тип проверяется по содержимому, имя файла не используется как путь.

### 8.6. Таблица и тай-брейки

Таблица считается по **записям (Entry)**. Порядок сортировки (каждый следующий пункт — только при равенстве предыдущих):
1. **Число побед** (бай при A7 — победа).
2. **Личная встреча** — только если ровно две записи равны по победам и сыграли друг с другом подтверждённый матч (выиграл — выше). Для трёх и более равных записей пункт пропускается.
3. **Разница сетов** (выигранные − проигранные); тех. поражения не учитываются.
4. **Разница геймов.**
5. **Меньше технических поражений.**
6. **Жребий**: `Standing.drawLot` — случайное число, сгенерированное при создании записи по сиду турнира; значение видит админ, при пересчётах не меняется.

Таблица пересчитывается транзакцией при каждом подтверждении матча. В UI рядом с местом знак «?» объясняет, по какому критерию разошлись места. Для одиночек считаются те же показатели по матчам, в которых играл он лично.

### 8.7. Распределение по дивизионам

После закрытия последнего квалификационного тура и обработки всех матчей (нет статусов `SCHEDULED/RESULT_SUBMITTED/DISPUTED/NEEDS_ADMIN`):
1. Отсортировать все `ACTIVE`-записи по §8.6 (места 1…N).
2. Нарезать: места 1–10 → дивизион 1, 11–20 → дивизион 2, остаток → дивизион 3 (`divisionSizes`). Если записей больше 30, остаток в третьем дивизионе окажется больше 10 — админу предупреждение «в третьем дивизионе N записей: оставить, увеличить или добавить четвёртый дивизион» (решает заказчик, §14, вопрос 5).
3. Если записей меньше 30, последний дивизион меньше 10; при размере меньше 6 админу предупреждение (мало для плей-оффа).
4. Записать `Entry.divisionId` и `divisionSeed` (место внутри дивизиона). Предпросмотр → «Опубликовать» → `Division.published = true`, рассылка игрокам.
5. Одиночки: сформировать **постоянные стороны плей-оффа** (A9): в пределах дивизиона отсортировать по рейтингу и соединить сильнейшего со слабейшим; нечётный остаток — решение админа вручную (§14, вопрос 7). Посев стороны — лучшее из двух мест.

Граница дивизионов проходит по таблице квалификации. При двух турах и 30 записях у части участников число побед совпадёт (в демо `demo/` у 14 из 30 пар по одной победе), и состав дивизионов определят тай-брейки. Об этом нужно сказать заказчику (§14, вопрос 6).

### 8.8. Плей-офф

Для дивизиона из N записей: размер сетки M — ближайшая степень двойки ≥ N (для 10 → 16). Посев по месту в дивизионе. Стандартная расстановка (пары 1–M, 2–(M−1)…) реализуется функцией `seedOrder(M)`; слот, у которого соперник «пустой» (посев > N), проходит дальше автоматически.

Для N = 10: **плей-ин** 7–10 и 8–9; **1/4**: 1 vs победитель(8–9), 4–5, 3–6, 2 vs победитель(7–10); **1/2**; **финал**. Пары 1–6 в плей-ине не играют.

- Раунды плей-оффа имеют свои сроки (A3: плей-ин 4 дня, 1/4 — 5, 1/2 — 5).
- Победитель подтверждённого матча автоматически идёт по `nextMatchId/nextMatchSlot`.
- Матчи плей-оффа создаются для всей сетки сразу (слоты ждут победителя) и «открываются», когда обе стороны известны; открытый матч получает дедлайн конца своего раунда по расписанию, а не «+N дней от открытия», чтобы турнир не растягивался (§14, вопрос 10).
- **Призовые места:** 1-е — победитель финала, 2-е — проигравший финалист. Матча за 3-е место нет (в концепте 2 призовых места на дивизион).
- Проигравшие плей-офф больше не играют. Чтобы выполнить цель «больше игр на площадках», можно добавить утешительный раунд (§14, вопрос 8) — вне MVP.
- Финал каждого дивизиона играется **офлайн в клубе** (`Tournament.finalsAt/finalsClubId`), результат вносит админ на месте (`resultSource = ADMIN`).
- `NEEDS_ADMIN` в плей-офф не закрывается автоматически: админ обязан выбрать победителя.

### 8.9. Рейтинг турнира («как у Lunda», A11)

- Шкала поля «рейтинг Lunda»: 1,0–7,0 (подтверждено по сайту Lunda). Мы **не имеем доступа** к их алгоритму и API и ничего у них автоматически не берём.
- Свой рейтинг турнира `User.internalRating` — целое число, Elo-подобное. Старт = `base + perLundaPoint × (lundaRating − lundaAnchor)`; без рейтинга Lunda — `base`. Значения по умолчанию (`base = 1000`, `perLundaPoint = 100`, `lundaAnchor = 3.0`) — **стартовая заглушка, подбирается позже по реальным данным**, а не факт о Lunda.
- После подтверждённого сыгранного матча: ожидание `E = 1 / (1 + 10^((Rb − Ra) / 400))`, где `Ra`, `Rb` — средние рейтинги сторон; новый рейтинг игрока `R' = R + K·(S − E)`, `S` = 1 при победе, 0 при поражении, `K = 32`. Тех. поражение рейтинг не меняет.
- Использование: подсказка при подборе пар одиночек (опция), справочный показатель в профиле. **На места в таблице рейтинг не влияет.**
- Указанный игроком рейтинг Lunda проверяет админ по скриншоту: статус `PENDING → VERIFIED/REJECTED`, админ может исправить значение. До проверки значение помечено «не проверен».
- **TODO (не блокирует разработку):** написать в Lunda про партнёрскую интеграцию (получение рейтинга по аккаунту/номеру); при положительном ответе добавить адаптер `LundaRatingProvider` вместо ручной проверки. Контакты брать на https://www.lundapadel.com/. Сообщение отправляет только заказчик или кто-то по его явному «да».

### 8.10. Призовой фонд и выплаты

Данные берутся **из фактически оплаченных записей**, суммы в копейках, округление вниз, остаток округления — организатору.

```
gross           = Σ expectedKopecks по платежам PAID/MANUAL_PAID
organizer       = floor(gross × 30%)                    // 30% организатору
fund            = gross − organizer                     // 70% в призовой фонд
divisionFund[i] = floor(fund × share[i])                // share = 60% / 30% / 10% (допущение: 60% — верхний дивизион)
place1[i]       = floor(divisionFund[i] × 70%)          // допущение A6
place2[i]       = divisionFund[i] − place1[i]
organizer      += fund − Σ divisionFund[i]              // остатки округления
```

Пример для 30 пар по 4000 ₽ (проверка расчёта): gross 120 000 ₽; организатору 36 000 ₽; фонд 84 000 ₽; дивизион 1 — 50 400 ₽ (1-е место 35 280 ₽, 2-е 15 120 ₽); дивизион 2 — 25 200 ₽ (17 640 / 7 560); дивизион 3 — 8 400 ₽ (5 880 / 2 520). **Это расчёт при допущениях A1 и A6, а не обещание призов:** на экране сумма всегда подписана «расчёт на N оплаченных записей», итоговые суммы утверждает организатор. Комиссия ЮMoney (по A10) уменьшает долю организатора. Если дивизионов меньше трёх, доли нормируются (§14, вопрос 15).

## 9. API

База: `https://<домен>/api/v1`. JSON; ошибки `{ "error": { "code": "STRING", "message": "…" } }`. Авторизация: `Authorization: Bearer <jwt>`, кроме отмеченных. Входные данные проверяются zod-схемами из `packages/shared`.

### 9.1. Авторизация Mini App

`POST /auth/telegram` (без токена): тело `{ initData: string }`. Сервер:
1. разбирает строку `initData`, берёт `hash`, строит `data_check_string` из остальных полей, отсортированных по имени, через `\n`;
2. считает `secret_key = HMAC_SHA256(key="WebAppData", message=BOT_TOKEN)` и проверяет `HMAC_SHA256(secret_key, data_check_string) == hash` (сравнение за постоянное время);
3. проверяет, что `auth_date` не старше `INITDATA_MAX_AGE_SEC` (по умолчанию 3600);
4. создаёт/обновляет `User` по `user.id`, выдаёт JWT на 24 часа.
Роль берётся из БД; Telegram-ID из `ADMIN_TELEGRAM_IDS` и `OWNER_TELEGRAM_ID` получают роль при первом входе.

## 10. Оплата через ЮMoney

### 10.1. Что подтверждено документацией (проверено 3 ноября 2026)

- Форма перевода (QuickPay): `POST https://yoomoney.ru/quickpay/confirm`. Обязательные параметры: `receiver` (номер кошелька), `quickpay-form=button`, `paymentType`, `sum`. Необязательные: `label` (до 64 символов), `successURL`. Источник: https://yoomoney.ru/docs/payment-buttons/using-api/forms
- Значения `paymentType` в документации: **`PC` — кошелёк ЮMoney, `AC` — банковская карта**. **СБП в этой форме не указан.** Комиссия удерживается с получателя: кошелёк — коэффициент 0,01 от суммы к получению; карта — 0,03 от суммы к списанию (при `sum = 4000` картой получатель получит 3880 ₽).
- HTTP-уведомление о входящем переводе: `POST`, `application/x-www-form-urlencoded`, UTF-8; приходит для переводов из кошелька (`p2p-incoming`) и для пополнений с карты через кнопку/форму (`card-incoming`); ЮMoney делает **три попытки**: сразу, через 10 минут, через час; ответ HTTP **200** = принято; рекомендован HTTPS. Источник: https://yoomoney.ru/docs/wallet/using-api/notification-p2p-incoming
- Поля уведомления: `notification_type, operation_id, amount` (зачислено), `withdraw_amount` (списано с плательщика), `currency` (643), `datetime, sender, codepro` (всегда false), `label, test_notification, unaccepted` (всегда false), `sign`. Поле `sha1_hash` **устарело и перестало приходить с 18 мая 2026** — использовать только `sign`.
- Подпись `sign` — **HMAC-SHA256 в HEX нижнего регистра** от строки из всех параметров кроме `sign`, отсортированных по имени (A–Z), значения URL-кодированы (UTF-8, RFC 3986), формат `ключ=значение`, разделитель `&`, пустые значения как `key=`; ключ — «секрет» из настроек HTTP-уведомлений.

### 10.2. Расхождение с концепцией: СБП

Концепция просит оплату «со СБП». По документации QuickPay для кошелька СБП недоступен. Варианты (решает заказчик, §14, вопрос 12):

| Вариант | Что это | Плюсы / риски |
|---|---|---|
| **A. QuickPay кошелёк/карта** | форма ЮMoney, HTTP-уведомления, автоподтверждение | поддержано документацией выше; СБП нет |
| **B. ЮKassa (магазин)** | подключение магазина, платёж через API, вебхуки статуса | возможен приём по СБП; **наличие СБП, условия и договор проверить в кабинете ЮKassa до начала разработки**; формат вебхуков другой |
| **C. Перевод по СБП вручную** | игрок переводит по номеру/QR, админ отмечает оплату | не автоматическое, противоречит требованию автоподтверждения |

Спецификация описывает вариант A и закладывает интерфейс `PaymentProvider`, чтобы позже заменить реализацию на ЮKassa без переделки остального кода.

### 10.3. Поток (вариант A)

1. Игрок нажимает «Оплатить». `POST /payments` создаёт `Payment`: `label = pay_<cuid>` (уникальный, ≤ 64 символов), `expectedKopecks` (400000 / 200000), `expiresAt = now + 24 ч`.
2. Сервер отдаёт страницу оплаты с HTML-формой (автоотправка) на `https://yoomoney.ru/quickpay/confirm` с полями `receiver`, `quickpay-form=button`, `paymentType` (выбор игрока: карта `AC` или кошелёк `PC`), `sum`, `label`, `successURL=https://t.me/<bot>/<app>?startapp=pay_<id>`. Открывать через `Telegram.WebApp.openLink` (внешний браузер), не во встроенном окне.
3. Игрок платит на стороне ЮMoney. ЮMoney шлёт `POST /webhooks/yoomoney`.
4. Обработчик (одна транзакция, идемпотентно):
   1. Прочитать тело как form-urlencoded; записать в `PaymentEvent` (с флагом результата проверки подписи).
   2. Вычислить `sign` по §10.1 и сравнить с присланным (за постоянное время). Не совпало → HTTP 400, платёж не трогать.
   3. `test_notification=true` → HTTP 200, платёж не менять.
   4. Найти `Payment` по `label`. Не найден → HTTP 200 (чтобы ЮMoney не повторял), событие остаётся в журнале, админ видит «платёж без заказа».
   5. `operation_id` уже обработан → HTTP 200 без действий (уникальность `Payment.operationId`).
   6. Проверить `currency=643`, `codepro=false`, `unaccepted=false` и **`withdraw_amount ≥ expectedKopecks/100`** (плательщик заплатил не меньше). Иначе платёж `MISMATCH`, запись не активируется, админу сигнал.
   7. Платёж → `PAID`, записать `operationId`, `receivedKopecks`, `withdrawKopecks`, `paidAt`; пересчитать статус `Entry` (§8.1); поставить уведомление игроку.
   8. Вернуть HTTP 200.
5. Mini App после возврата опрашивает `GET /payments/:id` каждые 5 секунд до 2 минут, затем показывает «проверяем» и кнопку связи.
6. Cron переводит просроченные платежи в `EXPIRED`; если по просроченному, но валидному `label` пришло уведомление, оно всё равно принимается (деньги получены).
7. Возвраты делает админ вручную в ЮMoney и отмечает в админке (`REFUNDED`).

Конфигурация: `YOOMONEY_RECEIVER`, `YOOMONEY_NOTIFICATION_SECRET`, `PUBLIC_BASE_URL`. **Секреты только в `.env`/секретах сервера — не в репозитории, логах и клиенте.** В логах платёжных событий маскируется `sender`.

Тесты (обязательны): верная подпись; неверная подпись; повтор `operation_id`; недоплата; платёж без `label`; тестовое уведомление; два одинаковых уведомления одновременно (гонка).

### 10.4. Ограничения и риски оплаты

- Сбор взносов и выплата призов — юридически значимая деятельность: форма регистрации организатора (самозанятый/ИП/юрлицо), налоги, лимиты и условия кошелька ЮMoney, оформление призов. **До запуска проконсультироваться с юристом/бухгалтером** (§14, вопрос 13). Спецификация этого не решает.
- Для кошелька могут действовать лимиты на остаток и входящие суммы в зависимости от статуса идентификации — проверить в личном кабинете.

## 16. Правила разработки

Эти правила продублированы в `.cursor/rules/project.mdc` (файл с `alwaysApply: true`; Cursor подхватывает его автоматически). Источник истины — файл в `.cursor/rules/`; текст ниже — его копия на дату версии 1.1 ТЗ.

Кратко:
- **Код:** TypeScript strict, ESLint + Prettier, структура `apps/*`, `packages/shared`, `design/`, `demo/`; турнирная логика — чистые функции без БД и без `Date.now()`/`Math.random()` внутри.
- **Процесс:** одна ветка на этап (`stage-<N>-<name>`), маленькие коммиты по Conventional Commits, один PR на этап.
- **Тесты обязательны:** тай-брейки, тех. поражения и дедлайны, жеребьёвка, сетка, призовой фонд, идемпотентность платёжного вебхука, проверка initData.
- **Безопасность:** никаких секретов в репозитории (`.env.example` вместо `.env`), никаких выдуманных клубов, спонсоров и призов.
- **Мок-данные сначала:** экран делаем на тестовых данных, утверждаем, затем подключаем API.
- **Дизайн:** минимум кнопок, цели касания 44–48 px, русские тексты.
- **Готовность этапа:** критерии приёмки закрыты, `lint/typecheck/test/build` зелёные, тесты правил на месте, нет секретов, экраны проверены на 360 и 390 px в двух темах, `CHANGELOG.md` обновлён.

- TypeScript в режиме `strict`, без `any` (исключение — комментарий с причиной), без `@ts-ignore`.
- ESLint + Prettier обязательны; перед коммитом должны проходить `pnpm lint` и `pnpm typecheck`.

- Сначала мок-данные, потом бэкенд: новый экран делается на тестовых данных (как в `demo/`), утверждается, затем подключается к API.

## Тесты (обязательны для бизнес-правил)
Без тестов не считается готовым:
- тай-брейки таблицы: каждый уровень (победы, личная встреча для двух, разница сетов, разница геймов, меньше тех. поражений, жребий) и случай трёх равных записей;
- тех. поражения и дедлайны: квалификация (обе стороны), плей-офф (`NEEDS_ADMIN`), продление срока, идемпотентность cron, граница суток в `Asia/Irkutsk`;
- жеребьёвка: воспроизводимость по сиду, отсутствие повторов соперников и напарников, бай;
- сетка плей-оффа для N = 8, 9, 10, 11, 12, 16 и продвижение победителей;
- призовые: сумма выплат + доля организатора = собранные взносы, округление, пример из §8.10;
- платёжный вебхук ЮMoney: верная и неверная подпись `sign`, повтор `operation_id` (идемпотентность), недоплата, платёж без `label`, тестовое уведомление, гонка двух одинаковых уведомлений;
- проверка подписи Telegram initData: валидная, подделанная, просроченная.
Тесты — Vitest. Для экранов — смоук-тесты Playwright.

## Мобильный дизайн (Telegram Mini App)
- Mobile-first. Тему брать из `--tg-theme-*`, поддерживать светлую и тёмную, учитывать `--tg-safe-area-inset-*`.
- На экране одно главное действие и не более двух второстепенных. Экран понятен за 3 секунды.
- Цели касания не меньше 44–48 px по высоте и ширине, основные кнопки 52 px, табы нижней навигации 64 px, строки таблицы 48 px, промежутки между целями не меньше 8 px.
- Текст не мельче 14 px, поля ввода не мельче 16 px. Иконки без подписи не использовать. Статус всегда и цветом, и текстом.
- Нативные `MainButton` и `BackButton` Telegram для главного действия и возврата.
